# 01 等待过程与操作反馈

> 状态：`[done]` —— 5 条全部完成

本册处理「用户点了，但不知道发生了什么」这类问题。

## 1-1 建立隧道时的等待缺少进展感 `P0`

### 现状

`cloudflared.rs:20` 的 `URL_TIMEOUT` 是 **30 秒**。用户点「映射」后：

- 按钮变为「建立中」+ 转圈（`create-tunnel-form.tsx:52`）。
- 除此之外**没有任何信息**，最长可能转 30 秒。
- 期间列表里不出现任何东西——因为条目是拿到链接后才 `insert` 的（`commands.rs` 的 `establish`）。

30 秒无变化的转圈，用户的合理判断是「卡死了」，而不是「在等」。而且这段时间里
`Starting` 这个状态**从未被使用过**——`TunnelStatus::Starting` 定义了却没有任何代码产生它。

### 改法

不改建立流程本身（仍是拿到链接才算成功），只补足等待期的表达：

1. 表单区在 pending 时显示一行随时间递进的提示文案，例如：
   - 0–3 秒：「正在启动 cloudflared…」
   - 3–10 秒：「正在向 Cloudflare 申请公网域名…」
   - 10 秒以后：「仍在等待，网络较慢时可能需要 30 秒」
   纯前端计时，不需要 Rust 侧回报进度。

2. 明确告知「最长等 30 秒」，让用户知道边界在哪，而不是无限期。

> 关于 `Starting` 状态：让它真正可用需要改 `establish` 为「先 insert 再异步等链接」，
> 这会动到建立流程与 registry 的时序，**超出本计划范围**。此处仅用前端计时表达等待，
> 并在 `09-improvements.md` 记下这条观察。

### 验收

点击映射后，等待期文案随时间变化；30 秒超时后错误提示与文案衔接得上。

## 1-2 复制成功的提示不诚实 `P1`

### 现状

`tunnel-card.tsx:98-101`：

```tsx
onClick={() => {
  void writeText(tunnel.publicUrl!);
  toast.success("链接已复制");
}}
```

`writeText` 的 Promise 被 `void` 丢掉，**无论成败都弹「已复制」**。
M5 修掉的 clipboard 权限缺失正是这类问题的温床——权限没配时复制其实失败了，
用户却看到成功提示，然后粘贴出一片空白。`engine-guard.tsx:43-46` 有同样写法。

### 改法

`await` 结果，成功才提示成功，失败给出可读错误：

```tsx
onClick={async () => {
  try {
    await writeText(tunnel.publicUrl!);
    toast.success("链接已复制");
  } catch {
    toast.error("复制失败，可手动选中链接复制");
  }
}}
```

配合 1-3：链接本身应可手选（已有 `.selectable`），错误提示里指向它才成立。

### 验收

正常情况提示成功；人为移除 clipboard 权限后应提示失败而非成功。

## 1-3 「在浏览器打开」失败无反馈 `P1`

### 现状

`tunnel-card.tsx:109`、`engine-guard.tsx:63` 均为 `onClick={() => void openUrl(...)}`。
打开失败（无默认浏览器、URL 异常）时**完全静默**，用户点了没反应，不知道是慢还是坏了。

### 改法

同 1-2，`await` 并在失败时 `toast.error("打开浏览器失败，链接已复制到剪贴板")`，
失败时顺手把链接放进剪贴板作为兜底——这不是新功能，是给已有操作补一个退路。

### 验收

正常打开无多余提示；失败时有明确错误。

## 1-4 断开操作没有确认，且提示语不分对象 `P1`

### 现状

- 断开按钮（`tunnel-card.tsx:117-126`）直接执行，无确认。断开会让**别人正在访问的链接立即失效**，
  且新链接无法恢复为旧的——这是不可逆操作。
- `use-tunnels.ts:79` 的提示恒为「映射已断开」，同时断开多条时无法分辨断的是哪条。

### 改法

1. 断开按钮改为需要二次确认。考虑到桌面应用的轻量定位，**不引入 Dialog 组件**，
   采用「点击后按钮原地变为『确认断开?』，3 秒内再点才执行，超时复原」的轻量模式，
   不新增依赖。
2. 提示语带上端口：「端口 3000 的映射已断开」。`stop`/`remove` 的 mutation 需要拿到 port，
   把参数从 `id: string` 改为 `{ id, port }`（仅前端改动，command 签名不变）。

> 若你更倾向「不加确认、保持一点即断的爽快」，本条可只做提示语部分。请在执行前告知取舍。

### 验收

误点不会立即断开；提示语能分辨具体是哪条。

## 1-5 移除记录同样静默 `P2`

### 现状

`use-tunnels.ts:89` 的 `useRemoveTunnel` 只有 `onSuccess: invalidate`，**没有任何 toast**。
用户点了垃圾桶，条目消失——虽然结果可见，但与其他操作的反馈风格不一致。

### 改法

补一条 `toast.success("记录已移除")`，与 1-4 一样带上端口。

### 验收

移除后有提示，风格与断开一致。
